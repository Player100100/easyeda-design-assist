# 架构

## 产品边界

核心是为 agent 补充辅助绘板的工程思路与取证工具。用户提出选型/拓扑问题后，agent 查询关联元件、网络和手册，形成绘制方案。手册作为可随时访问的原件维护，按问题查询；推理和推荐由 agent 完成。

设计助手面向正在变化的当前工程和局部操作上下文，输出建议并记录设计依据。`epro2-辅助绘制及审核` 面向冻结的 `.epro2` 版本，独立检查设计并形成审核档案。设计助手的建议不等于审核结论；审核项目不得把“曾经建议/采纳”当作 PASS 证据。

## 分层

```text
交互层（当前由 agent 对话承担）
  ├─ 收集目标、选中对象、工况和约束
  ├─ 选择 datasheet / selection / topology / schematic / pcb / local-check 任务
  └─ 展示建议、依据、风险和未决问题
        ↓
任务编排层（任务档案、检查状态、用户决定）
        ↓
工程指引与查询层
  ├─ 通用指引及六类模式 playbook，自动进入新任务 brief
  ├─ 手册原件访问、按需搜索、完整页阅读及可选原页渲染
  ├─ 单次原理图网表导出及按元件/网络的局部连接查询
  └─ agent 据实执行约束分析、推导、方案比较和验证规划
        ↓
数据适配层
  ├─ EasyEDA bridge（固定读取与受限原理图新增操作）
  ├─ 静态 BOM、手册、设计约束
  └─ 可复用的 epro2 解析/审核能力（暂不直接耦合）
        ↓
证据与记录层（外部 data 目录，带来源和时间）
```

当前已提供工程工作指引、连接查询、手册访问、任务编排、只读适配、受限写入和记录校验。交互推理由 agent 执行，字段完整性不能证明工程正确性。

## 核心对象

- `project`：项目目标/范围、有来源的需求、模块职责与接口、预算、方案决策、风险、任务依赖和验证追踪。`project-guide` 提供六阶段方法，`project-review` 检查记录缺项与关联任务，`project-impact` 沿显式引用传播影响，`project-revise` 保留修订证据与待复核项。详见 [项目级设计框架](project-design.md)。这些命令离线工作，不要求 CAD 连接。
- `drawing_plan`：目标身份、输入快照、用户请求、修改前后差异、依据、未决项及回读/失败处理记录。项目的 `drawing_policy` 管理触发与范围，`review-drawing-plan` 分别报告记录完整性和策略范围，不验证用户认可或执行 CAD。详见[自动绘图策略](autodraw-policy.md)。
- `context`：工程、焦点文档、文档类型、选中图元 ID、最多 100 个所选对象的允许属性、采集时间与连接窗口。v2 为图元详情逐项记录读取错误、缺失字段和支持状态；仍可读取 v1。
- `task`：唯一 ID、模式、目标、上下文快照、用户约束、缺失信息、状态和输出建议。
- `recommendation`：建议内容、对象定位、理由、证据、假设、风险、置信度、适用条件、验证动作及用户决定。
- `evidence`：来源类型、文件/URL/器件型号、文档修订、页码/章节、摘录或计算输入。手册事实和工程假设必须可区分。

任务状态采用 `draft → analyzing → needs_input / ready_for_user → accepted / rejected / deferred`。只有用户明确确认的决定才写成已采纳。绘图方案认可后可在方案范围内调用受限写接口；v2 器件放置已通过单器件实测，v3 空白原理图电路执行器为实验性实现，尚未实机验证。执行状态和锁语义见 `docs/circuit-executor.md`，实测范围见 `docs/live-api-verification.md`。

## API 边界

`schematic-connectivity` 保存一次固定 API 网表导出原文、哈希和范围；`inspect` 只在该快照内查询。具体接口、格式与范围限制见 `docs/connectivity.md`。手册索引作为查询工具，不预生成分类摘录。

`src/design_assist.py` 提供固定读取和受约束的器件、网络标号及导线新增调用，不接受 JavaScript 参数；方案中的结构化数据作为 JSON 传入固定代码。`drawing_circuit.py` 负责 v3 库归档几何核验、计划连接预检、固定调用及独立 Python 回读/网表/DRC 核对；`drawing_source.py` 检查旧图元保持不变，仅新增本步骤图元和其属性。API 的焦点文档和选中对象方法部分为 beta，调用失败时报告未取得上下文，不回退到不受约束的写接口。bridge 仅监听本机端口；多个窗口时明确指定窗口。

图元属性使用按文档类型和图元类型固定列出的 getter；详情接口为 beta，至多读取 100 个对象的属性，采集前后校验工程、焦点文档及选择集合。上下文保存 API 原字段名和原值，已知文档单位暂未实板校准，层字段保留原始编号。采集失败、ID 不一致和截断均写入版本化状态。API 连接不等于完整设计数据：连接关系、器件手册、板层叠层、工作电流、对端设备和工况仍需独立证据或用户输入；这些数据也不代表自动工程分析。

当前 `context` 在采集前后比对工程和焦点文档，多个已连接窗口必须指定 `--window-id`，请求始终携带窗口 ID，不修改 bridge 的全局活动窗口。它不能检测文档内部同时进行的编辑，因此只是一次读取记录，不能作为冻结的设计版本。

## 与审核项目的连接

两项目通过版本化文件格式交换，不共享运行状态或隐式结论。`handoff` 导出当前任务记录及其 SHA256；审核项目将其作为设计意图声明，仍需自行验证连接、器件限制和几何事实。当前不会自动复制外部来源文件，也不会绑定 `.epro2` 哈希，这些限制随清单明确记录。

暂不新建公共库：当前复用的是已有 bridge 的 HTTP 协议，不导入审核项目的脚本。`connect` 复用已有 bridge，缺失时启动已安装技能的后台服务；日志独立存放，不终止共享 bridge。待图元/网表模型在两个项目实际复用时，再抽出 `easyeda-common`，避免复制两套解析器。

## 后续演进顺序

1. 用真实绘制问题验证选型/拓扑指引，改进缺项识别、连接追踪和输出方案。
2. 完善手册来源发现和原页访问体验，保持型号、修订与工况可追溯。
3. 验证选中图元详情、PCB 单位/层映射和完整几何读取，扩充只读取证能力。
4. 用可追溯案例验证 PCB 回流、布线和铺铜指引；数值结论仍要求具体证据。
5. 按[自动绘图策略](autodraw-policy.md)完成 v3 电路执行器真实 CAD 验证，重点核对库几何、网络标号引脚、导线源差异及网表/DRC。现有多页工程增量编辑、属性修改、PCB 自动布局/布线和 UI 扩展按实际需求评估。
